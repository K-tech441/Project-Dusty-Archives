# 设计取舍 Q&A

这里记录方案里每一个"看起来可以不一样"的地方，以及为什么选了现在这条路。
每一条都来自真实踩坑或实测数据，不是先验偏好。

---

### Q1. 为什么不让 LLM 直接读 PDF 然后一次性输出 Lean？

因为它无法被检查。LLM 一次生成 1000 行 Lean，失败时你得到的是一个"看起来像证明"的
文本，没有可靠的办法定位错在定义、定理陈述还是证明。本方案把它拆成可检查的小步：
转录逐页可对账 → 原子逐条有 quote → 声明逐条有指针 → 判据逐条机械过。
**每一步的产物都能被机器否决**，这是能规模化的前提。

### Q2. 为什么 quote 存原文，而 Lean 只存指针？

因为两者的"稳定锚"不同：

- Markdown 转录没有稳定锚：不同版本/重排/OCR 重跑都会让行号漂移；
  而 quote 的判据本身就是"逐字连续子串"，存原文是唯一可机械验证的形态。
- Lean 有稳定锚：`.ilean` 给声明位置，探针给签名哈希，全限定名唯一。
  所以 `(模块, 位置, 签名哈希)` 足够定位，复制源码只会制造第二份真相。

### Q3. 为什么 atomic 清单要同时充当"工作单位"？

一开始 agent 是"按文件块"施工的：一次写 300–400 行，最后统一编译。实测问题是：
- 上下文一次装太多，越写越容易漂；
- 出错时难定位（一大块里哪条错了）；
- 清单最后统一填，容易漏项且无法中途验收。

改成"一次一个原子：声明 → 清单 → quote 校验 → 诊断 → 下一个"后：
单元小、可逐个验收、漏项立刻暴露、上下文不爆。**建模单位 = 引用单位 = 工作单位**，
这个统一是方案里收益最大的单点设计。

### Q4. 为什么判据必须只有一处实现？

因为判据一旦有第二份实现（grep、临时脚本、人工 checklist），两份就会漂移，
而漂移的判据比没有判据更危险——它会让"红"看起来像"绿"。
本方案所有判据（编译/公理/sorry/基底提及/判重/quote/模块卫生）都在同一个检查器里，
扩展判据 = 改那一处 + 跑全库回归。

### Q5. 为什么允许 `partial`（只证一部分）？

数学书里很多例子只写"同理可证"，完整形式化它的代价可能高于整节正文。
如果强制全部 verified，agent 会花巨大代价在边角上，或者偷偷用 sorry——后者不可接受。
`partial` 给出第三条路：**0 个 primary + 若干 witness**，诚实地记录"证了哪几小步"。
它仍进图、仍计数，读者能看出缺口在哪。

### Q6. 为什么只检查「陈述层」的引用？③a 和 ③a′ 到底各查什么？

先消歧。判据里有两条容易被混为一谈：

| 判据 | 查什么 | 输入 |
|---|---|---|
| **③a 提及** | 我们的模块是否**提及**禁止清单里的基底概念（那些我们要自造的东西） | `.ilean` 解析后的常量全名 + 定义所在模块 |
| **③a′ 基底范围** | 我们的**陈述层**（A 层）提及的 mathlib 名字是否都落在允许集里 | 图的 A 层边（来自签名范围） |

③a′ 的允许集由三部分组成：

- `base_candidate`：**从内容层支撑关系反向传播**得到的 mathlib 名字集合，并扣掉内容种子
  （它是生成物，不是手写的）；
- `scope_extras`：人工补登记的基底事实（例如 √ 这类反向传播覆盖不到、但确实允许用的）；
- core 原语命名空间（`Init` / `Std` / `Lean` / `Batteries`）。

注意两个容易错的直觉：

- 它**不是**"`Base.lean` 的 import 闭包"——允许集是按"内容实际需要什么支撑"算出来的；
- 它**不会**因为"这是语言原语"就放行：`Set` / `Function` 这些是 mathlib 名字，
  只有进了 `base_candidate` 或 `scope_extras` 才算允许。之前踩过 `Set.mem_range_self`
  出现在陈述层被 ③a′ 抓住——正确做法是写成 `⟨x, rfl⟩`，或把它留在证明层。

**为什么只查陈述层**：陈述是对外承诺的数学内容，检查它等于把"我们借用了什么"变成
可机械审计的边界；证明层（B 层）豁免，因为证明是"仪器"——tactic 展开物、基底内部引理
都在 B 层，混进检查会让判据失去意义。

**实践结论**：陈述层需要新事实时，走 `Base.lean` import + `基底.json` 登记的规程
（见 Q7），而不是随手 import；能改写成不引便利引理的形式（`rfl`、匿名构造）时优先改写。

### Q7. 为什么一边说"别重证基底"，一边又允许改基底？

判重（③b）防止内容层重新证明 mathlib 已有的事实；但基底本身是可扩展的
（书里用到的事实，mathlib 没有或形式不同）。所以规则是：
**基底可以加，但必须走固定流程 + 已验收节的全量回归**，避免"为了这节方便，
改坏了前面八节"。

### Q8. 为什么指针要带签名哈希，而不只是位置？

位置只保证"这里是某个声明"，不保证"还是同一条定理"。签名哈希把
"绑定器 + 类型"钉住：定理陈述被改（哪怕只是换等价写法），哈希变化，
校验立刻报"签名变了"，而不是安静地指向一个含义已变的声明。

### Q9. 为什么每次导图都要跑断言？

四层边的提取依赖编译产物与探针；任何一环过期都会**静默错分**（把 A 层提及算成
B 层，或漏掉整个模块），而图看起来仍然"正常"。断言（覆盖/幻影/守恒/级次）把
这类静默错误变成显式失败。实测中它抓到过聚合文件漏模块、`.ilean` 缺声明等问题。

### Q10. 为什么要 agent 分工（Lead / worker），不一个 agent 做全部？

因为"写"和"裁决"必须分开：写的人会对自己写的东西有偏见，尤其在被判据否决时
容易绕过去（写 `id` 包裹、降级 partial、删检查）。Lead 只做裁决与门禁，
worker 只做施工；写作用域不重叠，同一文件同时只有一个 writer。

### Q11. 为什么把流程规则注入系统提示，而不是每次任务书写一遍？

任务书每次由人/Lead 现写，必然漂移（实测：同一规则在两次任务书里出现了三个版本）。
把硬规则放进插件、每次调用注入，规则只有一份；任务书只写本节特殊信息。
代价是规则加载在启动时固化，改完要重启——这个代价被接受（手动重启）。

### Q12. 为什么用本地 mathlib 索引而不是在线检索？

在线检索（如 loogle 的公开服务）在无外网/代理受限的机器上经常不可用，
而检索是写证明时最高频的操作。本地 SQLite 索引（43 万声明 + FTS5）把检索变成
毫秒级、离线可用的能力，且结果可复现。

### Q13. 为什么记录 verdict 的"来源"？

因为出现过"某个文件被改了但不知道是谁改的"的情况（测试脚本、不同 agent 的 CLI 调用）。
现在是否每一份判据结果都带 `{origin, session, cwd, pid, ppid, argv}`，事后可归因。

### Q14. 这套东西能不用 DSH/插件吗？

能。核心是三个可独立存在的部件：判据检查器（CLI）、清单/图数据格式、以及
"agent 按原子施工"的流程模板。插件只是让"规则注入 + 工具暴露 + 面板渲染"更顺手。
最小依赖：一个能跑 Lean 的环境 + 一个能调 CLI 的 agent。

### Q15. 有评估数据吗？

当前是单实例（8 节 / 131 原子），样本不足以做统计评估。能说的经验判断是：
这条管线里大多数设计不是"更优选项"，而是**当前工程条件下的唯一可行解**——
例如判据唯一实现、quote 逐字、原子工作单位、A 层引用边界，都是在踩过对应坑之后
收敛出来的；换一种做法会在同一点以同样方式失败。
如果要正式评估，建议指标：原子覆盖率、verified 比例、人工干预次数/每节、单节成本。
